# 14. Глоссарий IPS, Interlink и Alvatune

## 1. Назначение и правила чтения

Этот глоссарий нужен не для буквального перевода старых названий, а для согласования **смысла** между продуктовыми специалистами IPS, разработчиками Interlink и командой Alvatune. Один и тот же русский или английский термин в этих системах нередко обозначает разные сущности. Поэтому в каждой строке указаны:

- рабочее определение;
- соответствие IPS и существенное отличие;
- владелец смысла в Interlink/Alvatune;
- статус и типичная ловушка;
- ссылки на подробное объяснение и исходные доказательства.

Короткие идентификаторы вида `[IL-PLM]`, `[IPS-A04]` и `[ALV-AGENT]` раскрываются в [реестре источников](15-source-register.md). Они важны: часть описаний IPS — историческая реконструкция, а часть Interlink — целевой контракт, ещё не доказанный исполняемым кодом.

### Метки статуса

| Метка | Значение |
|---|---|
| **Реализовано** | Поведение подтверждается текущим кодом и тестами в указанном срезе. |
| **Контракт** | Нормативно принято, но исполняемый путь готов не полностью. |
| **Цель** | Проектное направление после PoC; детали или бизнес-API ещё открыты. |
| **Хост** | Смысл принадлежит Alvatune либо другому приложению поверх Interlink. |
| **IPS** | Термин описывает исходную систему; точная семантика может зависеть от версии и конфигурации заказчика. |

Метка относится к функции, а не к наличию одноимённого типа. Например, наличие `SnapshotKind.Order` в контракте не означает готовый производственный заказ. Актуальная карта готовности находится в [02 — Текущее состояние и дорожная карта](02-current-state-and-roadmap.md).

## 2. Самые опасные перегрузки

| Слово | Какие разные смыслы скрывает | Как говорить однозначно |
|---|---|---|
| **Объект / object** | Устойчивая сущность IPS, её версия, строка БД, тип модели или бытовое «что угодно в системе». | `Identity`, `Revision`, `ObjectType` либо конкретный предметный тип: «деталь», «заказ». |
| **Версия / version** | Revision объекта, версия модуля, версия правила, токен внешнего ресурса, версия формата payload. | Всегда называть носитель: `Part Revision`, `ModuleVersion`, `PolicyVersion`, `ExternalVersionToken`. |
| **Контекст / context** | Контекст состава, редактирования, подбора, агента, актора, хранения или UI-окна. | Использовать полное имя: `CompositionContext`, `Changeset`, `ResolutionContext`, `ContextSnapshot`, `ActorContext`, `StorageContext`. |
| **Актуальная / текущая / последняя** | IPS base/current, назначенная `Current`, unique fixed `head`, политика `Latest`, состояние `Released`. | Не употреблять без точного термина и причины выбора. |
| **Связь / relation / link** | Хранимый first-class факт, место использования или generated-форма навигации. | `Relation`, `Occurrence` или `Link/Node` соответственно. |
| **Правило / rule** | IPS version-selection rule, правило конфигуратора, AutoMatch-сценарий, workflow condition, Interlink selection policy. | Называть класс: `ResolutionPolicy`, `PresencePredicate`, `AutoMatchRule`, `WorkflowRule`. |
| **Снимок / snapshot / baseline** | Итерация IPS, точный состав ПЗ, техническая проекция, бизнес-baseline, агентский `ContextSnapshot`. | Указывать вид: `Savepoint`, `Snapshot(kind=projection, baseline, order)`, `ContextSnapshot`. |
| **Изменение / change** | Извещение, рабочая копия, `Changeset`, `ChangeCase`, `Action` или внешний ECO. | Разделять контейнер предметных правок, процесс координации и исполняемую команду. |
| **Заказ / order** | Живой объект ПЗ, его строки, производственная потребность или неизменяемый `Order Snapshot`. | «ПЗ как живой объект» и «публикация состава ПЗ как `Snapshot(kind=order)`». |
| **Каталог / catalog** | Каталог модели, DB `meta`, НСИ/IMBase либо product catalog. | `ModelCatalog`, `meta catalog`, `business reference catalog`. |

## 3. Объект, версия и изменение

| Канонический термин | Определение | Соответствие и отличие в IPS | Место, статус и ловушка | Подробнее |
|---|---|---|---|---|
| **Object / объект** | Предмет, о котором система хранит данные. Само слово не определяет, идёт ли речь об устойчивой идентичности, состоянии или типе. | В IPS `Object` обычно является устойчивым владельцем набора `ObjectVersion`, но в UI «объектом» могут называть и выбранную версию. | В Interlink слово допустимо только на уровне общего рассуждения. В контрактах следует выбирать `Identity`, `Revision`, `Draft` или `ObjectType`. **Ловушка:** «ID объекта» без уточнения может означать identity ID либо revision ID. | [03 §5](03-core-concepts.md), [06 §4–5](06-ips-to-interlink-delta.md), [IL-PLM], [IPS-A01/A02] |
| **ObjectType / тип объекта** | Компилируемое определение конкретного предметного типа: versioned/nonversioned, атрибуты, иерархия, хранение и допустимые связи. | Ближайший аналог — тип объекта IPS, настраиваемый метаданными/Database Configurator. | **Контракт;** compiler/IR и G1/G2 реализованы, DB runtime ещё по фазам. Это не экземпляр и не экран карточки. Concrete type имеет type-owned физическое отображение, но при TPH типы могут делить таблицу. | [03 §4](03-core-concepts.md), [08 §2–6](08-model-delivery-and-extensibility.md), [IL-META], [IPS-A01] |
| **Identity / идентичность** | Устойчивое «что это», переживающее смену инженерных состояний; переносимый UUID и предметные identity-атрибуты. | Семантический аналог `Object` IPS и `config_id` Aras. | **Контракт; носители и generated shapes есть.** Identity не является «последней версией» и не содержит изменяемое revision-содержание. Человекочитаемое обозначение — атрибут, а не системная identity. | [03 §5](03-core-concepts.md), [07 §2.1](07-versioning-changes-snapshots.md), [IL-VERS-CONCEPTS] |
| **Revision / ревизия** | Зафиксированное состояние Identity. После commit предметное содержание неизменно; disposition — зрелость, применяемость и назначение Current — меняется только аудируемыми командами. | Аналог `ObjectVersion` IPS, но техническое сохранение не обязано создавать новую Revision. | **Контракт; полный writer впереди.** Revision не равна Draft, iteration, snapshot или module version. Историческая Revision может быть источником копирования содержания, но не создаёт параллельную ancestry-ветвь. | [07 §2.2, §4](07-versioning-changes-snapshots.md), [03 §5](03-core-concepts.md), [IL-VERS-SPEC] |
| **Draft / черновик** | Единственное изменяемое состояние versioned Identity; принадлежит одному открытому Changeset и видимо только в его overlay. | Покрывает содержательную часть рабочей копии IPS. | **Контракт; PoC-writer — следующая фаза.** Draft не является зафиксированной Revision и не должен быть виден обычному производственному чтению. Для существующей Identity он строится от unique fixed head. | [07 §2.3, §4–6](07-versioning-changes-snapshots.md), [IL-VERS-CONCEPTS] |
| **Working copy / рабочая копия** | IPS-механизм взятого на изменение состояния с блокировкой, базой и пользовательской изменяемостью. | Это исходный термин IPS; его пользовательская потребность сохраняется. | В Interlink это **не отдельный примитив**: `Draft + Changeset affected-object lock + overlay`. Нельзя переводить working copy только как Draft — потеряются контекст, блокировка и атомарность комплекта. | [07 §5](07-versioning-changes-snapshots.md), [06 §5](06-ips-to-interlink-delta.md), [IPS-A02], [IL-VERS-IPS] |
| **Iteration / итерация** | Промежуточно сохранённое состояние незавершённой работы IPS, пригодное для восстановления; в исторических реализациях охватывает атрибуты, файлы и связи. | Потребность «вернуться к сохранению» сохраняется, но iteration не становится новой продуктовой Revision. | В Interlink заменяется `Changeset Savepoint`. **Ловушка:** iteration IPS может быть источником миграционного evidence, но не следует автоматически превращать каждую iteration в Revision или business Snapshot. | [07 §5, §15](07-versioning-changes-snapshots.md), [04 §7](04-ips-functional-baseline.md), [IPS-A02], [IL-VERS-IPS] |
| **Savepoint / точка сохранения** | Именованный снимок **всего ожидающего состояния** открытого Changeset, который можно восстановить без изменения опубликованных данных. | Покрывает пользовательскую роль iteration IPS, но имеет более широкую атомарную границу: не одна рабочая копия, а весь комплект pending operations. | **Цель после PoC.** Не участвует в resolver, не является Revision, Baseline или точкой DB-транзакции, видимой как бизнес-версия. | [07 §5](07-versioning-changes-snapshots.md), [IL-VERS-CONCEPTS §2], [IL-VERS-SPEC] |
| **Generation / поколение** | Монотонный номер зафиксированных Revision одной Identity. | В IPS/Aras поколения и сохранения могут иметь иную гранулярность. | В Interlink назначается при commit осмысленной Revision, а не при каждом save. Не использовать как показатель maturity или module version. | [07 §2.2, §9](07-versioning-changes-snapshots.md), [IL-VERS-CONCEPTS], [IL-VERS-SPEC] |
| **Head / unique fixed head** | Конец зафиксированной ancestry-цепочки Identity, от которого создаётся следующий Draft. | Ближайшее понятие может восприниматься как «последняя версия», но это техническая роль линии истории, а не правило пользовательского чтения. | **Контракт.** Head не обязан совпадать с `Current`, `Released` или результатом `Latest`, например если крайняя Revision withdrawn/неeligible. Нельзя выбирать head неявно вместо policy. | [07 §4, §9](07-versioning-changes-snapshots.md), [IL-VERS-SPEC §3.2] |
| **Current / назначенная текущая** | Явно назначенная fixed Revision, максимум одна на Identity; отсутствие Current не вызывает скрытого fallback. | Заменяет базовую/`is_current`-семантику, но точное соответствие «базовой» и «актуальной» IPS нужно проверять по процессу заказчика. | **Целевой runtime фазы 4.** Current двигается только объявленной политикой или аудируемой командой. Не синоним head, Latest или Released. | [07 §9](07-versioning-changes-snapshots.md), [06 §5](06-ips-to-interlink-delta.md), [IL-VERS-CONCEPTS], [IPS-A02] |
| **Base version / базовая версия** | Термин IPS для версии, используемой по умолчанию в определённых сценариях. | Историческая семантика могла быть связана с lifecycle и настройкой типа. | В Interlink отдельного примитива нет: мигрируется в назначение `Current` и явную политику его продвижения. **Ловушка:** не переводить как head или Latest без customer decision table. | [07 §9, §19](07-versioning-changes-snapshots.md), [06 §5](06-ips-to-interlink-delta.md), [IPS-A02], [IL-VERS-IPS] |
| **Latest / последняя допустимая** | Selection policy, выбирающая newest eligible fixed generation после фильтрации по disposition; withdrawn по умолчанию исключается. | Похожа на «актуальную/последнюю» IPS, но задаётся явно в ResolutionContext. | **Целевой runtime фазы 6.** Это policy-result, а не флаг Revision. Не синоним Current или head; user predicates применяются после выбора eligible Revision, чтобы не «воскресить» старую. | [07 §8–9](07-versioning-changes-snapshots.md), [05 §8](05-composition-resolution.md), [IL-PLM] |
| **Released / выпущенная зона** | Revision в выпущенной зоне Maturity; policy `Released` выбирает newest eligible Revision этой зоны. | Покрывает часть шагов ЖЦ/уровней продвижения IPS. | **Контракт.** `Released` как зрелость не означает завершение конкретной workflow-задачи. Не синоним Current и не гарантия, что именно эта Revision входит в старый заказ. | [07 §7, §9](07-versioning-changes-snapshots.md), [IL-VERS-CONCEPTS] |
| **Maturity / инженерная зрелость** | Одна упорядоченная шкала стадий Revision с запечатанными поведенческими зонами: mutable, working, restricted, released, withdrawn; словарь стадий внутри зон настраиваем. | Сжимает относящиеся к версии части «шаг ЖЦ + уровень продвижения» IPS и `state + is_released` Aras. | **Контракт; carrier types есть.** Отвечает на пригодность Revision к выбору, но не на вопрос «кто сейчас согласует». Нельзя кодировать каждое состояние процесса как maturity stage. | [07 §2.5, §7](07-versioning-changes-snapshots.md), [03 §5](03-core-concepts.md), [IL-VERS-CONCEPTS] |
| **Lifecycle / жизненный цикл** | Широкое понятие: допустимые состояния, переходы, роли, проверки, согласования и история. | В IPS lifecycle совмещает предметную стадию версии и process behavior. | В новой системе разделён: Interlink владеет `Maturity` и инвариантами Revision; Alvatune/host — Workflow, tasks, approvals. **Ловушка:** lifecycle не является одним новым core enum. | [07 §7](07-versioning-changes-snapshots.md), [09 §3](09-alvatune-and-agents.md), [IPS-A02], [ALV-ADR068] |
| **Disposition / диспозиция** | Управляемые метаданные уже fixed Revision: maturity, effectivity, Current designation и другие разрешённые состояния, не переписывающие содержание. | В IPS подобные признаки распределены между lifecycle, base/actual и applicability. | **Контракт.** Disposition изменяется только typed-командами с аудитом. Не путать с content edit и workflow status. | [07 §2–7](07-versioning-changes-snapshots.md), [IL-VERS-CONCEPTS] |
| **Changeset / комплект изменения** | Единственный контейнер незавершённого предметного изменения: Drafts, typed pending operations, locks, overrides, target maturity/effectivity, preview/hash и атомарный commit. | Композицией покрывает working copy, editing context, linked contexts, notice/journal mechanics и групповое проведение. | **Полный Changeset — цель I1/после PoC;** минимальные writer primitives раньше. Это не Workflow, не ChangeCase и не просто список Revision. Второй writable Changeset в Alvatune запрещён. | [07 §2.4, §5–6](07-versioning-changes-snapshots.md), [09 §1–5](09-alvatune-and-agents.md), [IL-VERS-SPEC], [ALV-ADR068] |
| **Notice / извещение** | Управляемый процесс выпуска связанного изменения с причиной, затронутыми объектами, проверкой и подписями. | В IPS существует несколько предметных видов извещений и журнальные изменения. | В новой системе это `Changeset` как атомарное содержание **плюс** тип/церемония/Workflow хоста. Не отдельный способ записи и не синоним Changeset. | [07 §5, §15](07-versioning-changes-snapshots.md), [04 §5](04-ips-functional-baseline.md), [IPS-A09], [IL-VERS-IPS] |
| **ChangeCase / дело изменения** | Координационный aggregate/view Alvatune: intent, authority, exact subjects, Interlink Changeset, process, impact/evidence и внешний outcome. | Ближайшая продуктовая оболочка вокруг извещения/ECR/ECO, но может координировать и внешний PLM. | **Хост, целевой pilot.** ChangeCase не хранит второй mutable object graph и не коммитит Revision сам. | [09 §5–8](09-alvatune-and-agents.md), [10 §5](10-personas-and-scenarios.md), [ALV-TRANSITION] |
| **Workflow / процесс согласования** | Маршрут ролей, задач, approval, ожиданий и исключений вокруг изменения. | Соответствует process-части lifecycle/извещения IPS. | **Хост.** Может разрешить commit через `CommitPermit`, но не подменяет DB-инварианты Changeset. Process state не должен менять смысл resolver неявно. | [07 §7, §13](07-versioning-changes-snapshots.md), [09 §3, §5](09-alvatune-and-agents.md), [IL-HOST] |
| **ContentHash / хэш ожидаемого содержания** | Детерминированный хэш полного pending Changeset и точных model/policy/customization/file inputs, на которые распространяется решение. | В IPS approval/signature часто привязан к предметному комплекту, но единый canonical envelope требует проверки на целевой конфигурации. | **Контракт I1.** Изменение входов инвалидирует approval. Это не hash одной Revision и не замена авторизации. | [07 §6, §13](07-versioning-changes-snapshots.md), [09 §5, §14](09-alvatune-and-agents.md), [IL-HOST] |
| **CommitPermit** | Host-neutral доказательство, что авторизованное решение относится к текущему exact ContentHash и policy context. | Прямого универсального эквивалента IPS в исследованной модели нет; роль распределена между правами, lifecycle, workflow и подписью. | **Контракт I1.** Permit не является правом сам по себе и не делает Workflow частью Interlink. Ядро повторно сверяет содержание перед атомарным commit. | [07 §13](07-versioning-changes-snapshots.md), [09 §14](09-alvatune-and-agents.md), [IL-HOST], [ALV-ADR068] |

## 4. Контексты, подбор версии и объяснимость

| Канонический термин | Определение | Соответствие и отличие в IPS | Место, статус и ловушка | Подробнее |
|---|---|---|---|---|
| **Context / контекст** | Набор явных входов, ограничивающих смысл операции. Само слово не задаёт ни область, ни срок жизни. | В IPS контекст может означать UI/session editing context или composition view. | В Interlink/Alvatune слово без квалификатора считается неоднозначным. Всегда уточнять один из типов ниже. | [05 §2–5](05-composition-resolution.md), [07 §3](07-versioning-changes-snapshots.md), [09 §11](09-alvatune-and-agents.md) |
| **Editing context / контекст редактирования** | IPS-объект, содержащий exact versions, которые должны быть видны совместно при редактировании; мог быть активным состоянием session/window. | Сохраняется потребность видеть незавершённый согласованный комплект. | Заменяется `Changeset read overlay`: query получает exact ChangesetId. Ambient «активный контекст окна» не переносится. **Ловушка:** не равен CompositionContext или ResolutionContext целиком. | [05 §4.6, §7.4](05-composition-resolution.md), [07 §5](07-versioning-changes-snapshots.md), [IPS-A05/K04] |
| **Linked context / связанный контекст** | Группа editing contexts IPS, согласованно влияющих на подбор; не должна содержать две версии одной Identity. | Исторический способ объединить несколько контекстов/изменений. | Обычно сворачивается в один multi-object Changeset; сложная независимая координация — в ordered bundle/host process. **Цель после PoC.** Нельзя оставлять несколько равноприоритетных overlays одного объекта. | [05 §4.6, §7.4](05-composition-resolution.md), [07 §5](07-versioning-changes-snapshots.md), [IPS-A05/K04], [IL-VERS-IPS] |
| **ResolutionContext / контекст подбора** | Immutable явный набор входов resolver: policies, per-edge policies, snapshot selection, coordinates, ChangesetId и fallback. | Заменяет комбинацию текущего правила, active context, applicability и пользовательских preferences IPS как скрытого session state. | **Контракт; SQL resolver впереди.** Context отвечает «что выбрать сейчас», но не гарантирует тот же результат после изменения данных; для межвременной фиксации нужен Snapshot. | [03 §13](03-core-concepts.md), [05 §7.3, §8](05-composition-resolution.md), [07 §8](07-versioning-changes-snapshots.md), [IL-PLM] |
| **Resolver / функция подбора** | Одна каноническая функция выбора exact target Revision для occurrence/identity по явному контексту. | В IPS порядок механизмов исторически расходится между источниками и мог зависеть от версии/configuration. | **Целевой порядок:** `Snapshot → Pin → Changeset → Effectivity → Policy → explicit Fallback/NoMatch`. **Ловушка:** это осознанный контракт Interlink, а не заявление о точном порядке всех IPS-инсталляций. | [05 §5, §8](05-composition-resolution.md), [06 §7](06-ips-to-interlink-delta.md), [07 §8](07-versioning-changes-snapshots.md), [IPS-A04/K03/K04] |
| **ResolutionReason / причина подбора** | Машиночитаемое объяснение выбранной Revision или отсутствия результата: Snapshot, ExactPin, ChangesetDraft, Effectivity, Policy, Fallback, NoMatch. | IPS мог показывать происхождение выбора и «не совсем подходящую» версию, но единый canonical reason нужно проверять по модулю/версии. | **Контракт фазы 6+.** Причина — часть результата/evidence, а не только diagnostic log. Нельзя терять reason при материализации DTO или Snapshot. | [03 §11, §13](03-core-concepts.md), [07 §8](07-versioning-changes-snapshots.md), [05 §8](05-composition-resolution.md), [IL-QUERY] |
| **Concretion / конкретизация** | IPS-механизм предпочтения либо фиксации конкретной child version для связи/контекста. | Имеет hard и soft разновидности с разной долговечностью и precedence. | В Interlink общего примитива `Concretion` нет: hard → `Pin`, soft → Changeset `Override`. Так исключается похожее имя для двух разных видов состояния. | [05 §4.5, §7.2–7.4](05-composition-resolution.md), [06 §5](06-ips-to-interlink-delta.md), [IPS-A04] |
| **Hard concretion / жёсткая конкретизация** | Долговременное требование использовать exact Revision цели occurrence. | В IPS имеет высокий приоритет и должна ссылаться на version того же child object. | Заменяется `Pin`. **Ловушка:** это данные состава, а не пользовательская policy и не «текущий выбор». | [05 §4.5, §7.2](05-composition-resolution.md), [07 §2.6](07-versioning-changes-snapshots.md), [IPS-A04], [IL-VERS-IPS] |
| **Soft concretion / мягкая конкретизация** | Временное preference пользователя/изменения к child version, не обязательно остающееся после проведения. | В IPS могла сбрасываться или восстанавливаться на lifecycle transitions. | Заменяется `Changeset Override`, видимым только внутри overlay. Перед commit override удаляется либо явно превращается в Pin. **Цель после PoC.** Не хранить как вечное свойство occurrence. | [05 §4.5, §7.4](05-composition-resolution.md), [07 §5, §15](07-versioning-changes-snapshots.md), [IPS-A04], [IL-VERS-SPEC] |
| **Override / переопределение** | Временное точное preference в контексте одного Changeset. | Функционально покрывает soft concretion IPS. | **Цель full Changeset.** Имеет меньшую долговечность, чем Pin, и не может тихо пережить commit. Не синоним policy override в администрировании модели. | [07 §5–6](07-versioning-changes-snapshots.md), [05 §7.4](05-composition-resolution.md), [IL-VERS-SPEC] |
| **Pin / точная фиксация** | Exact target Revision на relation/occurrence; сильнее effectivity и policy. | Прямое функциональное соответствие hard concretion IPS и Fixed-link Aras. | **Контракт; recursive pins — фаза 5.** Composite FK должен доказать, что Revision принадлежит TargetIdentity. Pin фиксирует одно ребро, но сам по себе не доказывает точность всего многоуровневого графа. | [03 §13](03-core-concepts.md), [05 §7.2](05-composition-resolution.md), [07 §2.6, §8](07-versioning-changes-snapshots.md), [IL-VERS-SPEC] |
| **Applicability / применяемость** | Бизнес-вопрос «для какого головного изделия, серии, даты или иных условий допустима эта Revision/позиция». | В IPS часть данных исторически кодировалась строками; подтверждены head/series/date и annulment. | В новом словаре потребность остаётся, физический механизм называется `Effectivity` над typed axes. **Ловушка:** применяемость не равна maturity, presence или editing context. | [05 §4.4, §7.5](05-composition-resolution.md), [06 §8](06-ips-to-interlink-delta.md), [IPS-A04/K03] |
| **Effectivity** | Нормализованное декларативное утверждение о применимости Revision к Coordinates; ranges и непересечение доступны БД. | Покрывает IPS applicability/effectivity semantics, но устраняет encoded multi-value strings и делает precedence явным. | **Цель OC-A.** Не определяет присутствие Occurrence и не выбирает option variant: edge presence проверяется отдельно до resolver-а. Не меняет содержимое Revision и не является policy; конкретный head сильнее wildcard, serial сильнее date. | [05 §7.5, §8](05-composition-resolution.md), [07 §2.7](07-versioning-changes-snapshots.md), [IL-VERS-SPEC], [IPS-A04] |
| **Coordinates / координаты** | Canonical typed map значений объявленных axes, например head product, serial и date, передаваемый в ResolutionContext. | В IPS соответствующие значения могли поступать из статусов, заказа, UI и конфигуратора разными путями. | **Контракт осей; полноценное исполнение — OC-A/OC-B.** В OC-A coordinates постоянны на весь traversal; path-scoped propagation относится к OC-B. Не путать с геометрическими координатами CAD. | [05 §7.5, §7.7](05-composition-resolution.md), [IL-PLM], [IL-ADR ADR-051–052] |
| **Axis / ось** | Объявленное измерение контекста конфигурации/применяемости с типом и правилами значений. | Аналоги — головное изделие, серия, дата, опции IPS. | **Контракт/цель.** Axis является частью модели, а не произвольной строкой UI. `CompositionContext` может быть axis/value или typed predicate, если это принято моделью. | [05 §7.5, §7.7](05-composition-resolution.md), [08 §2–6](08-model-delivery-and-extensibility.md), [IL-META] |
| **Rule / правило** | Общее имя исполняемого условия/вычисления. В IPS version-selection rule — lifecycle object с обычными criteria и дополнительным min/max criterion. | IPS также использует правила в конфигураторе, AutoMatch, формах и workflow; это не один движок с одним смыслом. | В Interlink слово без квалификатора запрещено в product contract. Resolver использует `Policy`; presence — predicate; AutoMatch — domain rule service; workflow — host. **Ловушка:** не переносить произвольный второй rule engine в kernel. | [05 §4.2, §6.4, §7.6](05-composition-resolution.md), [06 §9](06-ips-to-interlink-delta.md), [IPS-A04/A11] |
| **Policy / политика подбора** | Именованная, версионируемая стратегия выбора Revision после pin/changeset/effectivity: Current, Released, Latest, MinMaturity, PinnedOnly либо compiled enterprise policy. | Покрывает роль current version-selection rule IPS, но имеет фиксированное место в едином resolver. | **Built-in contracts есть; runtime планируется в P4/P6.** Особый `PinnedOnly`: если Pin отсутствует, Changeset/Effectivity не продолжают обычный подбор; разрешён только explicit fallback либо `NoMatch`, а root должен быть exact. Policy не является approval policy, authorization policy или Workflow. | [05 §7.6, §8](05-composition-resolution.md), [07 §8–9](07-versioning-changes-snapshots.md), [IL-PLM], [IL-QUERY] |
| **Fallback / запасной подбор** | Явно разрешённая вторичная policy, применяемая только если primary selection не дал Revision; возвращает warning/reason. | Сохраняет полезное поведение IPS «не совсем подходящая», где min/max мог выбрать version из не прошедших основные criteria. | **Контракт фазы 6.** Fallback никогда не маскируется под ordinary match. Для production/order его допустимость должна задаваться политикой; без разрешения результат `NoMatch`. | [05 §4.3, §7.6, §8](05-composition-resolution.md), [07 §8](07-versioning-changes-snapshots.md), [IPS-K03/A04], [IL-ADR ADR-042/044] |
| **NoMatch / нет подходящей ревизии** | Канонический исход, когда included occurrence не может получить target Revision и fallback не разрешён. | В IPS UI мог предпочесть «не совсем подходящую» version пустой ветви. | **Контракт.** Это не то же самое, что occurrence, исключённое presence predicate. В snapshot-safe traversal любой рекурсивный NoMatch отклоняет публикацию всего Snapshot. | [05 §8–9](05-composition-resolution.md), [07 §8, §12](07-versioning-changes-snapshots.md), [IL-VERS-SPEC] |

## 5. Состав, место использования и конфигурация

| Канонический термин | Определение | Соответствие и отличие в IPS | Место, статус и ловушка | Подробнее |
|---|---|---|---|---|
| **Relation / типизированная связь** | First-class typed факт с собственной identity, attributes, endpoint constraints, cardinality и навигационными фразами. | Соответствует relation IPS как самостоятельной сущности с GUID и атрибутами. | **Метамодель/G1-G2 реализованы; DB writer/query впереди.** Relation не равна reference attribute, generated Link или всякой строке join-table. | [03 §6, §9](03-core-concepts.md), [05 §3.1](05-composition-resolution.md), [IL-META], [IPS-A03] |
| **Occurrence / вхождение, место использования** | Специализированная структурная Relation: exact source Revision использует target Identity; хранит quantity, unit, position, order, pin и domain attributes места. | Прямая нормализация асимметрии IPS `ObjectVersion parent → Object child`. | **Контракт/G2 forms есть; runtime позже.** Количество и позиция принадлежат occurrence, не child object. Occurrence row принадлежит source Revision; target Revision выбирается при чтении. | [03 §6](03-core-concepts.md), [05 §3, §7.1](05-composition-resolution.md), [IL-PLM], [IPS-A03] |
| **Occurrence identity / ID строки вхождения** | Идентичность конкретной relation-row внутри одной source Revision. | Близка GUID relation IPS. | Не гарантирует непрерывность позиции между revisions родителя. Для этой задачи используется `occurrence_thread_id`. Нельзя адресовать долговечный внешний факт только row ID. | [03 §6](03-core-concepts.md), [05 §7.8](05-composition-resolution.md), [IL-PLM] |
| **Occurrence thread / нить вхождения** | Стабильная identity lineage позиции через revisions состава: inherited occurrence сохраняет thread; новая позиция получает новый. | В исследованной продуктовой модели IPS relation ID не даёт явно подтверждённой cross-revision identity позиции. | **Принят контракт ADR-050/052; registry — фаза 3.** Thread не равен occurrence row, target Identity, position number или полному адресу. Повторное использование завершённой нити запрещено. | [03 §6](03-core-concepts.md), [05 §7.8](05-composition-resolution.md), [IL-PLM], [IL-ADR ADR-050/052] |
| **ThreadPath / путь нитей** | Последовательность occurrence threads от exact root до конкретного места в развёрнутой структуре. | В IPS путь обычно восстанавливается traversal-ом relation, но отдельный канонический cross-revision locator публично не подтверждён. | **Контракт G4/DT.** Полный live-address: `(StructureDefinitionId, ExactRootRevisionId, ThreadPath)`. Одна thread недостаточна, если reused subassembly встречается под разными parents. | [03 §6](03-core-concepts.md), [05 §7.8, §8](05-composition-resolution.md), [IL-PLM], [IL-ADR ADR-052] |
| **Identity path / путь объектов** | Последовательность source/target identities при traversal. | Обычное представление ветви состава. | Полезен для чтения, но не заменяет ThreadPath: одинаковые компоненты могут повторяться на разных местах. Для diff/внешних фактов нужен путь нитей. | [05 §3.4, §7.8](05-composition-resolution.md), [IL-PLM] |
| **StructureDefinition** | Точное определение того, какую типизированную структуру и в каком направлении разворачивать. | В IPS роль частично задают типы relations, views и контексты состава. | **Контракт G4.** Входит в полный адрес позиции и provenance Snapshot. Не синоним root object или CompositionContext. | [03 §6](03-core-concepts.md), [05 §8–9](05-composition-resolution.md), [IL-QUERY], [IL-PLM] |
| **Composition / состав** | Граф объявленных occurrences и результат их контекстного включения/разрешения. | IPS формирует состав из relations, context, applicability, concretion, rules, options и replacements. | В Interlink это не один механизм: occurrence physics + presence + resolver + substitution + traversal + optional Snapshot. **Ловушка:** «состав» может означать source structure, live resolved graph или exact publication — нужно уточнять. | [05 §1–2](05-composition-resolution.md), [04 §5](04-ips-functional-baseline.md), [IPS-A03–A05] |
| **Composition context / контекст состава** | Предметный вид структуры: общий, конструкторский, технологический, производственный и т.п.; определяет, какие occurrences рассматриваются. | Подтверждённый механизм IPS для разных представлений одной структуры. | В Interlink должен быть model-declared axis/value либо typed occurrence predicate. **Цель OC-A/OC-B.** Не равен editing context, ResolutionContext или UI-tab. | [05 §3.3, §7.7](05-composition-resolution.md), [04 §5](04-ips-functional-baseline.md), [IPS-A03] |
| **Presence predicate / условие присутствия** | Типизированное условие, решающее, входит ли occurrence в выбранную configuration environment **до** выбора target Revision. | Соответствует variant/option conditions конфигуратора IPS. | **Цель OC-A/OC-B.** Исключённое occurrence не является NoMatch; trace должен различать `excluded` и `included but unresolved`. Не синоним Effectivity Revision. | [05 §7.7, §8](05-composition-resolution.md), [06 §8](06-ips-to-interlink-delta.md), [IL-META], [IPS-A05] |
| **Configurator / конфигуратор** | Предметная система опций, допустимых значений, incompatibilities, implications, defaults, presence и propagation, строящая разрешённую комплектацию. | Сохраняет конфигуратор IPS и его роль в формировании точного изделия/заказа. | **Целевой domain contract, не готовый core engine.** Interlink даёт typed model/axes/predicates/resolver; enterprise module/host даёт каталог опций, UX и process. Нельзя считать наличием `Coordinates` готовый configurator. | [05 §6.1, §7.7](05-composition-resolution.md), [06 §8](06-ips-to-interlink-delta.md), [IL-META], [IPS-A05] |
| **Option / опция** | Самостоятельный типизированный параметр конфигурации с кодом, категорией, типом и допустимыми values. | Прямо соответствует опциям IPS. | **Цель domain module.** Нужно различать absent value, explicit «не выбрано» и default; смешение даёт неверную комплектацию. Option не является произвольным string key в ResolutionContext. | [05 §6.1](05-composition-resolution.md), [04 §5](04-ips-functional-baseline.md), [IPS-A05] |
| **Configuration environment / среда конфигурации** | Набор option/axis values и path-scoped наследования, в котором проверяются presence и resolution. | В IPS формируется конфигуратором, заказом и propagation значений. | **Цель:** constant coordinates в OC-A, scoped propagation/nested configurations в OC-B. Не путать с software environment или customer model deployment. | [05 §7.7, §8–10](05-composition-resolution.md), [IL-ADR ADR-052] |
| **Substitution / допустимая замена** | Composition-scoped N:M-конструкция group → variants → members, где один variant может заменить набор позиций другим совместным набором. | Соответствует допустимым заменам IPS для конкретного состава. | **Цель после PoC.** Привязывается к thread/path scope. Не сводится к `replacement_id`, не равна global Analog и не является новой Revision child object. | [05 §6.2, §10](05-composition-resolution.md), [06 §8](06-ips-to-interlink-delta.md), [IPS-A05], [IL-META] |
| **Variant / вариант замены или конфигурации** | Один допустимый совместный набор members внутри substitution/configuration group. | IPS допускает один актуальный и альтернативные варианты, в том числе несколько occurrences в одном варианте. | **Цель domain model.** Слово перегружено: не путать variant комплектации, Revision и software variant. Всегда указывать group/context. | [05 §6.2, §10](05-composition-resolution.md), [IPS-A05] |
| **Analog / аналог** | Глобально допустимый заменитель object с периодом, приоритетом и режимом выбора, потенциально применимый во многих compositions. | Прямой предметный механизм IPS. | Базовый identity-scoped candidate set выразим `list<reference<T>>`; **полный behavior остаётся целью domain service/model** и должен добавить период, priority, mode, reason/provenance. Не равен composition-scoped Substitution: аналог может быть глобальным, а допустимая замена привязана к конкретному месту/набору мест. | [05 §6.3, §10](05-composition-resolution.md), [04 §5](04-ips-functional-baseline.md), [IPS-A04] |
| **AutoMatch / Expert** | Версионируемый технологический сценарий подбора/расчёта с typed inputs, candidate constraints, conditions, formulas/actions и trace. | Сохраняет важную функцию IPS технологического подбора. | **Хост/domain service, не второй resolver kernel.** Воспроизводимость требует exact rule version, exact input snapshot, units, candidate/exclusion trace и результата. Proposal/добавление в состав проходит typed Action/Changeset. | [05 §6.4, §10](05-composition-resolution.md), [06 §9](06-ips-to-interlink-delta.md), [04 §5](04-ips-functional-baseline.md), [IPS-A11] |

## 6. Точные конфигурации, заказы и производственные артефакты

| Канонический термин | Определение | Соответствие и отличие в IPS | Место, статус и ловушка | Подробнее |
|---|---|---|---|---|
| **Live resolved graph / живой разрешённый состав** | Результат чтения текущих occurrences с применением presence и resolver в переданном ResolutionContext. | Соответствует динамически сформированному составу IPS в текущем контексте. | **Целевой G4/resolver.** Может измениться после публикации новых Revision, Effectivity или Policy. Даже одинаковый ResolutionContext не гарантирует тот же межвременной результат. Не использовать как evidence старого выпуска. | [05 §1–2, §8–9](05-composition-resolution.md), [07 §2.8, §8](07-versioning-changes-snapshots.md), [IL-PLM] |
| **Exact composition / точный состав** | Полный граф с однозначно выбранной exact Revision на каждом включённом месте и сохранёнными occurrence payload/reasons. | В IPS точный состав возникает в заказе, точном изделии и иных предметных фиксациях; универсальная standalone Baseline публично не подтверждена. | В Interlink точность достигается либо all-edge pins в ограниченном случае, либо `Snapshot` полного графа. **Ловушка:** несколько pinned верхних рёбер ещё не делают весь рекурсивный состав exact. | [05 §2, §9](05-composition-resolution.md), [07 §10–12, §15](07-versioning-changes-snapshots.md), [IPS-A13], [IL-VERS-IPS] |
| **Snapshot / снимок конфигурации** | Материализованный exact full graph: exact root, topology, resolved revisions, occurrence payload, reasons, normalized context и exact model/policy/customization provenance. | Систематизирует потребности IPS в точном заказе и зафиксированных предметных состояниях; не является утверждением, что IPS имел один универсальный Snapshot API. | **Минимальный projection — фаза 8; business kinds после PoC.** Snapshot не произвольно отфильтрованный report: snapshot-safe traversal идёт до листьев, а любой NoMatch отклоняет batch. | [03 §15](03-core-concepts.md), [07 §10–12](07-versioning-changes-snapshots.md), [05 §9](05-composition-resolution.md), [IL-PLM] |
| **Projection Snapshot / `kind=projection`** | Техническая immutable-на-время-жизни materialization полного exact graph для ускорения чтения; перестраивается созданием нового ID. | Прямого универсального аналога IPS в исследованной документации нет; отдельные caches/projections не доказывают ту же семантику. | **PoC-фаза 8.** Может быть удалён privileged maintenance и не является business evidence. Не путать с Alvatune read projection, SQL view, report export или Baseline. | [07 §10–12, §18](07-versioning-changes-snapshots.md), [03 §15](03-core-concepts.md), [IL-VERS-SPEC] |
| **Baseline Snapshot / `kind=baseline`** | Append-only бессрочное бизнес-свидетельство exact конфигурации для выпуска, обмена, отчёта или аудита. | Универсальная сущность Baseline уровня Windchill в IPS публично не подтверждена; заказ и iteration являются предметными источниками фиксированных состояний, но не тождественны Baseline. | **Цель после PoC.** Не обновляется и не удаляется обычным путём; whole-artifact authorization. Может потребовать отдельный self-contained evidence artifact, если ссылки на source Revision недостаточны юридически. | [07 §10–12](07-versioning-changes-snapshots.md), [04 §7](04-ips-functional-baseline.md), [IL-PLM], [IPS-DOSSIER] |
| **Order Snapshot / `kind=order`** | Append-only точный полный состав одной публикации/передачи живого производственного заказа. | Покрывает требование IPS: будущие изменения изделия, rules и settings не меняют уже переданный состав ПЗ. | **Цель после OC-A.** Живой заказ может иметь много Order Snapshots. Snapshot не хранит цены, сроки, workflow и весь объект заказа как core primitive. Не синоним ПЗ. | [07 §10, §15](07-versioning-changes-snapshots.md), [05 §9](05-composition-resolution.md), [04 §5](04-ips-functional-baseline.md), [IPS-A13], [IL-VERS-IPS] |
| **Snapshot locator** | Стабильный адрес строки уже опубликованного snapshot: `(SnapshotId, Seq)`; thread path восстанавливается из topology. | IPS-адресация точной строки заказа зависит от конкретной реализации. | **Контракт.** Не заменяет live-address `(StructureDefinitionId, ExactRootRevisionId, ThreadPath)` и не должен использоваться для нового live traversal. | [05 §14](05-composition-resolution.md), [07 §11–12](07-versioning-changes-snapshots.md), [IL-PLM] |
| **Provenance / происхождение результата** | Exact сведения, позволяющие понять, из каких model/policy/customization/rule/input versions и кем получен результат. | В IPS часть происхождения находится в versions, contexts, rules, order и audit; полнота зависит от module/configuration. | В Interlink входит в Snapshot/Revision change trail; в Alvatune — также в ContextSnapshot/ActionRun/AgentRun. **Ловушка:** audit timestamp без exact artifacts не обеспечивает воспроизводимость. | [07 §11, §14](07-versioning-changes-snapshots.md), [09 §9–12](09-alvatune-and-agents.md), [IL-PLM], [ALV-AGENT] |
| **Exact product / точное изделие** | Предметный объект, полученный из configurable product для выбранной комплектации и имеющий собственную Identity/историю; его structure должна быть exact для заявленной точки фиксации. | IPS прямо допускает создание точного изделия из конфигурируемой сборки, не разрушая исходную структуру. | **Цель enterprise domain, не core primitive.** Моделируется как конкретный ObjectType с exact references/pins и при необходимости Baseline. Не синоним Order Snapshot, ПЗ, отдельного serialised as-built экземпляра или просто «текущего resolved BOM». | [05 §6.1, §9](05-composition-resolution.md), [04 §5](04-ips-functional-baseline.md), [IPS-A05], [IPS-A13] |
| **Exact object / объект без подбора Revision** | Target, для которого relation/snapshot form уже адресует точный nonversioned/identity-like предмет и resolver Revision не требуется. | В IPS часть объектов может быть неверсионной либо уже точной. | **Контракт ADR-052.** Не следует автоматически называть каждый exact-object «точным изделием»: первое — форма адресации, второе — бизнес-артефакт конфигурации. | [03 §7](03-core-concepts.md), [05 §4.1](05-composition-resolution.md), [IL-ADR ADR-052], [IL-VERS-IPS] |
| **Head product / головное изделие** | Product/assembly, относительно которого интерпретируются series/date applicability и конфигурация. | Подтверждённый вход применяемости IPS; historically nonversioned type/handler semantics могли отличаться. | В Interlink — typed coordinate/Identity по declared head axis. Не синоним root Revision traversal: один и тот же root может читаться для разных product/program contexts по принятой модели. | [05 §4.4, §7.5](05-composition-resolution.md), [04 §5](04-ips-functional-baseline.md), [IPS-A04], [IL-VERS-SPEC] |
| **Production order / PZ / ПЗ / производственный заказ** | Живой versioned предметный объект: что и в каком количестве изготовить, в какие сроки и комплектации; содержит/формирует точный состав передачи. `PZ` — только латинская транслитерация русской аббревиатуры `ПЗ`, не отдельный английский стандартный термин. | В IPS ПЗ одновременно является production artifact и editing context для подбора технологических объектов. | В новой системе ПЗ — **enterprise ObjectType + host process**; каждая передача фиксируется отдельным Order Snapshot. **Цель после PoC.** ПЗ не является Snapshot и не должно превращать order workflow в kernel primitive. | [04 §5, сценарий C](04-ips-functional-baseline.md), [05 §9](05-composition-resolution.md), [07 §10, §15](07-versioning-changes-snapshots.md), [IPS-A13], [IL-HOST] |
| **Production sheet / PV / ПВ / производственная ведомость** | Версионный производственный документ с карточкой, собственным составом, context редактирования, проверкой, согласованием, подписью и отчётами/заявками. `PV` — латинская транслитерация `ПВ`, а не общепринятый международный PLM-код. | Самостоятельный модуль/артефакт IPS; может создаваться по прототипу, использовать base versions и аналоги. | **Enterprise domain + Alvatune workflow/files/signatures**, не core Snapshot kind. Её versioned structure может храниться в Interlink, exact публикация — Baseline/Order Snapshot по продуктовой роли. ПВ не синоним ПЗ и не просто печатная форма. | [04 §5, сценарии C–E](04-ips-functional-baseline.md), [06 §13, §15](06-ips-to-interlink-delta.md), [IPS-A13], [IPS-A06/A09] |
| **Order line / строка заказа** | Occurrence живого ПЗ, включая требуемое изделие, quantity, options/ZIP и другие данные конкретной потребности. | В IPS строки участвуют в формировании состава заказа и могут приводить к instances/lots. | **Цель enterprise model.** Не путать с snapshot entry: первая редактируема через Revision/Changeset живого ПЗ, вторая immutable и относится к одной публикации. | [05 §9](05-composition-resolution.md), [07 §10–12](07-versioning-changes-snapshots.md), [IPS-A13] |
| **Individual / экземпляр изделия** | Конкретная физическая единица с serial identity и фактической историей. | IPS различает экземпляры и партии при планировании/выпуске. | **Будущий digital-twin/domain track.** Не Revision проекта и не exact product definition. Связь с design occurrence должна использовать thread/path и exact source evidence. | [04 §5, сценарий C](04-ips-functional-baseline.md), [05 §7.8](05-composition-resolution.md), [IPS-A13], [IL-ADR ADR-050/052] |
| **Lot / batch / партия** | Группа физически учитываемых единиц с общим production/traceability контекстом. | IPS поддерживает партийный учёт, отличный от учёта каждого экземпляра. | **Будущий domain track/ERP-MES integration.** Партия не является Revision, Snapshot или quantity на BOM occurrence. | [04 §5, сценарий C](04-ips-functional-baseline.md), [IPS-A13] |

Это не approval, не ActionRun result и не mutation. Второй mutable `ChangeProposal` object container запрещён. | [09 §12–13](09-alvatune-and-agents.md), [06 §9, §16](06-ips-to-interlink-delta.md), [ALV-TRANSITION], [ALV-AGENT] |
| **Action** | Versioned typed authorizable/idempotent application command Alvatune: declared intent/input/effect/recovery, направляемый к правильному владельцу данных. | IPS-команды UI/module могут решать похожую задачу, но не образуют подтверждённый единый governance envelope. | **Alvatune target.** Internal object Action вызывает exact Interlink command/Changeset; external Action — connector operation. Action не является object writer, Changeset или approval. | [09 §12](09-alvatune-and-agents.md), [06 §15–17](06-ips-to-interlink-delta.md), [ALV-TRANSITION], [ALV-AGENT] |
| **ActionRun** | Immutable/append-oriented envelope одного исполнения Action: intent, exact input, policy, approval, attempts, result и evidence. | Прямого универсального аналога IPS нет; части находятся в audit/integration journals. | **Alvatune app target.** Не domain Evidence автоматически и не ChangeCase/Changeset. Transport success не обязательно означает business completion. | [09 §9, §12](09-alvatune-and-agents.md), [ALV-TRANSITION], [ALV-AGENT] |
| **AgentRequest** | Typed запрос агента человеку/process: clarification, missing context, authority, approval, budget или exception remediation. | Ближайший UX-аналог — задача/запрос уточнения, но с явным machine-readable типом. | **Alvatune app target.** Free-form comment не выдаёт разрешение и не закрывает request неявно. Это runtime state, не Interlink Revision. | [09 §7, §9–10](09-alvatune-and-agents.md), [ALV-AGENT] |
| **Internal authority / внутренняя авторитетность** | Режим, где Interlink является SoR внутреннего object state, а Alvatune — SoR process/work/policy state. | Применим при замене/создании внутреннего PLM-контура, а не при работе рядом с внешней IPS. | **Принятая целевая граница.** Object mutation идёт через Interlink Changeset; process audit/outbox — Alvatune. Не означает, что Interlink владеет workflow, файлами или UI. | [09 §1–5](09-alvatune-and-agents.md), [ALV-ADR068], [ALV-TRANSITION] |
| **Federated mode / внешняя авторитетность** | Режим, где внешний PLM остаётся единственным SoR для конкретного object/process/resource state; Alvatune наблюдает, координирует и выдаёт разрешённые commands. | Это основной вариант сосуществования с действующей IPS без немедленной миграции её данных. | **Alvatune target.** Interlink остаётся единственным **внутренним** object kernel, но не присваивает authority внешних объектов. Не синоним двусторонней синхронизации, local writable mirror или import. | [09 §6](09-alvatune-and-agents.md), [06 §17](06-ips-to-interlink-delta.md), [ALV-ADR070], [ALV-TRANSITION] |
| **Delegated execution** | Режим, где Alvatune владеет parent intent/process, а внешний provider исполняет child operation и остаётся authority его результата. | Похож на запуск операции в IPS/ERP из внешнего workflow. | **Alvatune target.** Completion подтверждается observation/reconciliation, а не фактом отправки request. Не смешивать с external authority всего ChangeCase. | [09 §6, §12](09-alvatune-and-agents.md), [ALV-TRANSITION], [ALV-AGENT] |
| **ExternalResourceRef** | Stable provider namespace/type/ID с optional exact version/configuration token; URL/display key — только навигация. | Соответствует ссылке на object/version IPS при федеративной работе. | **Alvatune integration target.** Не локальная Identity и не гарантия свежести; точное состояние подтверждает ExternalObservation. | [09 §6, §11](09-alvatune-and-agents.md), [06 §17](06-ips-to-interlink-delta.md), [ALV-TRANSITION] |
| **ExternalObservation** | Immutable наблюдение состояния внешнего SoR с version/sequence/freshness и mapping version. | Аналог снимка ответа IPS API/integration journal, но с явной семантикой наблюдения. | **Alvatune integration target.** Не writable replica, не Interlink Revision и не вечная истина после истечения freshness. | [09 §6, §11, §17](09-alvatune-and-agents.md), [06 §17](06-ips-to-interlink-delta.md), [ALV-TRANSITION] |
| **Connector capability** | Декларированная способность adapter: reference/observe/prepare/start/command/reconcile и гарантии идемпотентности/recovery. | IPS XML/API/Bridge предоставляет поверхности, но их exact guarantees нужно проверять по версии и операции. | **Alvatune integration target.** Capability не равна authority и не позволяет агенту расширять permissions. | [09 §6, §12, §17](09-alvatune-and-agents.md), [06 §17](06-ips-to-interlink-delta.md), [IPS-A15], [ALV-TRANSITION] |
| **Reconciliation / сверка результата** | Evidence-based сопоставление local intent/request с authoritative external state, особенно после ambiguous outcome. | В IPS integrations аналогичная потребность возникает при потерянном ответе/повторной передаче. | **Хост/integration.** Нельзя blind-retry операцию с возможным side effect. Reconciliation не означает слияние двух равноправных object truths. | [09 §6, §12, §19](09-alvatune-and-agents.md), [06 §17](06-ips-to-interlink-delta.md), [ALV-AGENT] |
| **Evidence / доказательство** | Управляемый business/governance artifact с provenance, digest, exact subject и applicability. | В IPS документы, подписи, журналы и exact order могут служить evidence, но это разные артефакты. | Durable domain Evidence может быть Interlink object; app audit row сам по себе не становится Evidence. Не путать с log, ContextSnapshot или Snapshot, хотя они могут входить в evidence package. | [09 §3, §8–12](09-alvatune-and-agents.md), [07 §11–14](07-versioning-changes-snapshots.md), [ALV-ADR068], [ALV-AGENT] |
| **Projection / read model Alvatune** | Rebuildable представление Inbox, ChangeCase, Process Monitor, search/calendar поверх authoritative sources. | IPS UI views/search results решают похожую read-задачу. | **Хост target.** Переход выполняется у source, а не редактированием projection. Не синоним `Snapshot(kind=projection)` и не business evidence. | [09 §7–9](09-alvatune-and-agents.md), [06 §12, §15](06-ips-to-interlink-delta.md), [ALV-ADR070] |

## 9. As-designed, as-built и as-maintained

Эти термины описывают **разные временные и авторитетные представления продукта**, а не стадии одной Revision. Их нельзя заменять словом «актуальный состав».

| Канонический термин | Определение | Связь с IPS | Место, статус и ловушка | Подробнее |
|---|---|---|---|---|
| **As-designed / как спроектировано** | Инженерное намерение: design identities/revisions, requirements и структура, обычно в конкретном ResolutionContext либо Baseline. | Соответствует конструкторскому составу/КД IPS. | Interlink умеет моделировать design graph; exact исторический as-designed требует Baseline, а live current view остаётся динамическим. Не обязательно released и не равно as-built. | [04 §5, сценарии A–B](04-ips-functional-baseline.md), [05 §2–3](05-composition-resolution.md), [07 §10–12](07-versioning-changes-snapshots.md), [IPS-A03] |
| **As-released / как выпущено** | Exact approved design configuration на момент выпуска с release evidence. | Соответствует выпущенной КД/зафиксированному предметному результату IPS. | Обычно `Baseline Snapshot + approval/evidence`; не просто policy `Released` на каждом ребре при сегодняшнем чтении. Полезный промежуточный термин между as-designed и production. | [07 §9–13](07-versioning-changes-snapshots.md), [04 §5](04-ips-functional-baseline.md), [IPS-A09] |
| **As-planned / как запланировано** | Технологический/производственный план: process, resources, norms, substitutions и потребность до фактического изготовления. | Соответствует технологическому/производственному составу, техпроцессам, ПВ и планированию IPS. | Domain modules поверх Interlink + host planning/integration. Не равно as-designed, Order Snapshot или факту исполнения. | [04 §5, сценарии C–D](04-ips-functional-baseline.md), [10 §4, §8](10-personas-and-scenarios.md), [IPS-A11/A13] |
| **As-ordered / как заказано** | Exact configuration и quantities, переданные для конкретного производственного заказа. | Соответствует точному составу ПЗ IPS. | Целевой `Order Snapshot` плюс business fields живого ПЗ. Не доказывает, что изготовлено без отклонений. | [05 §9](05-composition-resolution.md), [07 §10, §15](07-versioning-changes-snapshots.md), [IPS-A13] |
| **As-built / как изготовлено** | Фактический состав конкретного serialized individual или lot: реально установленные компоненты, serial/lot, deviations и substitutions. | IPS поддерживает instances/lots и производственный контур, но полнота конкретного as-built профиля должна проверяться на инсталляции. | **Будущий DT/domain track.** Факты ссылаются на design/order evidence и occurrence thread/path, но не переписывают as-designed Revision. Не синоним Order Snapshot: заказанное и изготовленное могут различаться. | [04 §5, сценарий C](04-ips-functional-baseline.md), [05 §7.8](05-composition-resolution.md), [IPS-A13], [IL-ADR ADR-050/052] |
| **As-maintained / как обслуживается сейчас/на дату** | Фактическая конфигурация физического individual после service events: installs/removals/repairs/modifications, разрешённая на указанную дату. | IPS-критика и смежные PLM-материалы требуют эксплуатационного контура, но он не считается полностью подтверждённой функцией базового IPS. | **Будущий MRO/DT domain, вероятно federated.** Это time-dependent fold событий поверх as-built, не «последняя design Revision» и не перезаписанный единственный состав. Для аудита нужен event history и temporal query. | [06 §17](06-ips-to-interlink-delta.md), [09 §6](09-alvatune-and-agents.md), [IPS-CRITIQUE], [IL-PRECEDENTS] |
| **Digital thread / цифровая нить** | Прослеживаемая цепь exact references/evidence между requirements, design, released, planned, ordered, built и maintained representations. | IPS связывает многие из этих артефактов, но единая сквозная модель зависит от modules/integration. | Не один DB table и не occurrence thread. `OccurrenceThreadId` — локальный строительный блок адресации места; digital thread — продуктовая сеть provenance/relations через жизненный цикл. | [03 §6](03-core-concepts.md), [07 §14](07-versioning-changes-snapshots.md), [09 §5–12](09-alvatune-and-agents.md) |

## 10. Что нельзя считать синонимами

| Нельзя уравнивать | Почему | Корректная формулировка |
|---|---|---|
| `Object = Identity = Revision` | Предмет, его устойчивая identity и одно состояние — разные уровни. | «Revision R принадлежит Identity I типа Part». |
| `Draft = working copy` | Draft — mutable content; working-copy behavior также требует Changeset, lock и overlay. | «Draft в Changeset реализует рабочую копию». |
| `Iteration = Revision` | Iteration сохраняет незавершённую работу; Revision — осмысленный immutable commit. | «IPS iteration мигрируется в Savepoint, если нет отдельной причины считать её business revision». |
| `Savepoint = Snapshot` | Savepoint восстанавливает pending change; Snapshot фиксирует exact published graph. | Указывать `Changeset Savepoint` или `Snapshot(kind=...)`. |
| `Current = Head = Latest = Released` | Это designation, ancestry end, selection policy и maturity eligibility. | Указывать exact policy/reason: `Policy(Current)` или `Policy(Released)`. |
| `Maturity = Workflow state` | Maturity влияет на пригодность Revision; workflow описывает работу людей/агентов. | «Revision released; ChangeCase awaiting signature». |
| `Changeset = ChangeCase = Action` | Это контейнер object changes, coordination aggregate и application command. | «Action запускает command в exact Changeset, координируемый ChangeCase». |
| `EditingContext = CompositionContext = ResolutionContext` | Первый даёт overlay работы, второй выбирает вид структуры, третий задаёт весь подбор. | Называть полные типы контекста. |
| `Pin = Snapshot` | Pin фиксирует одно target edge; Snapshot — полный граф и provenance. | «Occurrence pinned; full configuration published as Baseline». |
| `Effectivity = Presence = Policy` | Они отвечают «где/когда revision применима», «входит ли edge» и «какую eligible revision выбрать». | Описывать порядок: presence → pin/changeset/effectivity/policy. |
| `Fallback = ordinary match` | Fallback означает, что primary criteria не дали результата. | Показывать warning и `ResolutionReason=PolicyFallback(...)`. |
| `NoMatch = excluded occurrence` | NoMatch — включённая позиция без target Revision; excluded edge не входит в configuration. | Хранить разные trace outcomes. |
| `Relation = Occurrence = Link = Reference` | Хранимый typed fact, structural specialization, read form и field value имеют разные invariants. | Выбирать механизм по identity/attributes/navigation semantics. |
| `Occurrence row ID = thread = path` | Это строка одной Revision, lineage позиции и полный адрес от root. | Для live-address использовать root + StructureDefinition + ThreadPath. |
| `Substitution = Analog` | Первая composition/path-scoped и может быть N:M; второй глобальнее и имеет period/priority/mode. | «Допустимая замена этой группы» против «аналог детали». |
| `Rule = Policy` | Rule — перегруженный класс logic; Policy — конкретный слой revision resolver. | `ResolutionPolicy`, `PresencePredicate`, `AutoMatchRule`. |
| `Exact product = ПЗ = ПВ = Order Snapshot` | Это product instance/definition, заказ, производственный документ и immutable публикация состава. | Называть бизнес-объект и вид его exact evidence отдельно. |
| `Baseline = Projection Snapshot` | Business evidence бессрочно; projection — rebuildable acceleration. | `Snapshot(kind=baseline)` против `kind=projection`. |
| `Interlink Snapshot = ContextSnapshot` | Первый фиксирует object graph; второй — permissioned AI input manifest. | «AgentRun used ContextSnapshot C referencing Baseline B». |
| `Projection Snapshot = Alvatune projection` | Первый — exact graph cache; второй — rebuildable UI/read model из нескольких SoR. | Всегда указывать owner/kind. |
| `Record = object` | Record — generated DTO формы чтения, не универсальный domain primitive. | «PartRevisionRecord материализует Revision результата». |
| `Descriptor = catalog = meta` | Descriptor описывает один definition, ModelCatalog объединяет G1, DB meta хранит deployment projection/delta. | Указывать уровень и storage. |
| `Actor = Principal` | Actor объясняет происхождение; principal участвует в authorization. | «Agent actor действует on behalf of principal P». |
| `Proposal = Action = Approval` | Candidate, исполняемая intent-команда и решение о допустимости — разные состояния. | «Proposal validated → Action preview → approval → execution». |
| `Connector capability = authority` | Техническая способность читать/писать не делает систему владельцем истины. | Отдельно фиксировать authority mode каждого resource/state. |
| `ExternalObservation = imported Revision` | Observation — неизменяемый факт чтения с freshness; import создаёт внутренний authoritative object по отдельному решению. | «Наблюдаем IPS», либо «выполнен reviewed authority transfer». |
| `As-designed = as-built = as-maintained` | Намерение, факт изготовления и эксплуатационное состояние расходятся во времени и по authority. | Сравнивать exact representations через links/evidence, не перезаписывать одно другим. |

## 11. Рекомендуемый язык в продуктовых обсуждениях

### Вместо неоднозначных фраз

| Неудачная фраза | Рекомендуемая фраза |
|---|---|
| «Открываем актуальную версию детали». | «Resolver выбирает `Policy(Current)`; если Current отсутствует, возвращается NoMatch без fallback». |
| «Контекст подставил рабочую версию». | «Query с `ChangesetId=...` выбрал собственный Draft с reason `ChangesetDraft`». |
| «Связь закреплена». | «Occurrence имеет exact `PinnedRevisionId`; остальные рёбра этой ветви остаются динамическими». |
| «Сохранили состав». | «Опубликован полный `Snapshot(kind=baseline)` от exact root; NoMatch отсутствует». |
| «Заказ — это snapshot». | «ПЗ остаётся живым versioned объектом; передача №3 зафиксирована Order Snapshot». |
| «Агент изменил объект». | «AgentRun создал typed Proposal; после policy/approval Action вызвал command в exact Changeset». |
| «Мы синхронизируем IPS». | «IPS остаётся authority; Alvatune хранит ExternalObservations и отправляет разрешённые commands с reconciliation». |
| «Это as-built состав». | «Это Order Snapshot as-ordered; фактические serial/lot installations as-built ещё не получены». |

### Минимальная формула точного утверждения

Для любого спорного результата достаточно назвать шесть вещей:

```text
subject Identity / exact root Revision
+ structure definition and direction
+ ResolutionContext / authority mode
+ selected exact Revisions and ResolutionReasons
+ model/policy/rule/input versions
+ publication or observation artifact and actor
```

Если хотя бы один элемент неизвестен, следует говорить «live view», «наблюдение» или «реконструируемое предположение», а не «точный подтверждённый состав».
