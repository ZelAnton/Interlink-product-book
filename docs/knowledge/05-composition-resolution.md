# 05. Формирование состава: IPS → Interlink

## 1. Главный ответ

Прежняя функциональность формирования состава IPS достигается в Interlink не переносом одного «механизма состава», а композицией независимых механизмов:

```text
1. Occurrence хранит место использования: исходная ревизия → целевая идентичность.
2. Предикат включения решает, входит ли место в выбранную конфигурацию.
3. Механизм разрешения выбирает точную целевую ревизию по явному ResolutionContext.
4. Механизмы замены и конфигурации выбирают допустимый вариант позиций.
5. G4 разворачивает полный граф, сохраняя пути, полезную нагрузку и причины.
6. Snapshot фиксирует 100%-результат, когда он должен быть воспроизводимым.
```

Так сохраняется результат IPS — контекстно сформированный инженерный состав, — но исчезает зависимость от скрытого состояния окна, распределённого порядка правил и повторного подбора производством.

Критическая граница: в текущем коде реализованы носители и контракты генерации кода, но исполняемые G4, механизм разрешения, Effectivity, конфигуратор и Snapshot производственного заказа ещё не готовы. Полный ответ ниже описывает целевую архитектуру с фазовыми статусами.

## 2. Что означает «состав»

Нужно различать минимум шесть понятий.

| Понятие | Вопрос |
|---|---|
| Исходная структура | Какие места использования объявлены у исходной ревизии? |
| Контекст состава | Какой вид структуры нужен: общий, конструкторский, технологический, производственный? |
| Подбор ревизии | Какое состояние целевой идентичности использовать? |
| Вариантность | Входит ли Occurrence при выбранных опциях и координатах? |
| Замена/аналог | Какой набор позиций или глобальный объект допустим вместо исходного? |
| Точная конфигурация | Какой полный разрешённый граф был утверждён или передан? |

IPS реализует эти задачи отдельными механизмами, которые могут участвовать в одном чтении. Interlink делает их границы и порядок частью контракта.

## 3. Базовая модель состава IPS

### 3.1. Асимметричная связь (Relation)

Ключевая семантика IPS:

```text
ObjectVersion родителя ──Relation──> Object ребёнка
```

Relation — самостоятельная типизированная сущность с ID/GUID и атрибутами. В старой физической модели `F_PROJ_ID` адресует ревизию-владельца, а `F_PART_ID` — дочерний объект. [IPS-A03], [IPS-M02].

Преимущество: новая ревизия компонента не требует переписывать все родительские связи.

Цена: Relation ещё не определяет точную дочернюю ревизию. Её нужно выбрать при чтении.

### 3.2. Данные места использования

Relation/Occurrence несёт:

- количество и единицу измерения;
- позицию и номер позиции;
- порядок сортировки;
- примечание;
- контекст состава;
- ссылку конкретизации или ревизии;
- атрибуты применяемости и варианта;
- предметно-специфичные данные вхождения.

Эти значения относятся к использованию компонента в конкретном составе, а не к карточке компонента. [IPS-A03].

### 3.3. Контексты состава

Подтверждены представления:

- общий;
- конструкторский;
- технологический;
- производственный.

Они фильтруют вхождения одной структуры, позволяя различным ролям видеть свои представления без копирования дочерних объектов. Контекст состава не равен контексту редактирования.

### 3.4. Рекурсивный граф

Состав читается вниз, а применяемость и обратный поиск вхождений — вверх. Повторно используемый компонент может встречаться в разных ветвях и несколько раз под одним корнем. Физически это ориентированный граф; нормативно корректный состав должен быть DAG. Ошибочные циклы обязаны обнаруживаться и обрабатываться по явной cycle policy, поэтому структуру нельзя считать деревом, идентифицируемым только парой «родитель/ребёнок».

## 4. Подбор версии в IPS

### 4.1. Кандидаты

Для целевого объекта существует набор ревизий. Система должна дать для Occurrence ровно одну ревизию либо явно показать конфликт или отсутствие результата. Подбор ревизии требуется не для всех типов объектов; для неверсионируемой цели этот шаг пропускается. [IPS-K03 §1].

### 4.2. Правило подбора

Rule — объект IPS с жизненным циклом. Существуют общие, персональные и системные правила. Критерий содержит:

- атрибут ревизии;
- функцию сравнения;
- отрицание;
- константу, пользовательскую переменную или значение другого атрибута.

Обычные критерии объединяются операторами AND/OR. Дополнительный агрегатный критерий выбирает минимум или максимум среди нескольких кандидатов. В исторической реализации Rule содержит минимум один обычный и ровно один агрегатный критерий. [IPS-K03 §2].

### 4.3. Резервный результат «не совсем подходящая»

Исторический алгоритм:

1. Отобрать ревизии по обычным критериям.
2. Если одна — вернуть её.
3. Если несколько — выбрать минимум или максимум дополнительным критерием.
4. Если ни одной — применить выбор минимума или максимума к неподошедшим ревизиям.
5. Вернуть результат со статусом «не совсем подходящая».

Это штатный результат, а не авария. Пользовательский интерфейс должен был его подсветить. [IPS-K03 §3], [IPS-A04].

Продуктовый смысл: IPS предпочитает показать пригодный резервный результат вместо пустой ветви. Риск: последующий процесс может принять предупреждение за обычный точный результат.

### 4.4. Применяемость

Ревизия может быть применима:

- для конкретного головного изделия либо по шаблону;
- по диапазону серийных номеров или серий;
- по диапазону дат;
- с признаком аннулирования.

Для одного целевого объекта и головного изделия диапазоны разных ревизий не должны пересекаться. Исторически данные кодировались строкой в многозначном атрибуте, поэтому для них нельзя было создать полноценный индекс диапазона и ограничение, запрещающее пересечения. [IPS-K03 §5], [IPS-A04].

### 4.5. Конкретизация

- жёсткая конкретизация (`hard concretion`) задаёт точную дочернюю ревизию и имеет высший приоритет в актуальной реконструкции;
- мягкая конкретизация (`soft concretion`) — временное пользовательское предпочтение, разрешённое для данного типа Occurrence;
- конкретизированная ревизия обязана принадлежать целевому объекту.

Мягкая конкретизация могла сбрасываться и восстанавливаться при переходах жизненного цикла. [IPS-A04].

### 4.6. Контекст редактирования

Контекст редактирования (`Editing context`) — обычный версионируемый объект, содержащий список точных ревизий и номер группы связанных контекстов.

Инвариант: в связанной группе не может быть двух ревизий одного объекта. Иначе механизм разрешения получил бы несколько кандидатов с одинаковым приоритетом. Объект Notice может выступать контекстом редактирования. [IPS-K04 §1–§3], [IPS-A05].

Историческая проблема: активный контекст был состоянием сеанса или окна. Переключение могло повлиять на фоновую задачу, забытое автозаполнение добавляло лишние ревизии, а несколько окон требовали синхронизации пользовательского состояния. [IPS-K04 §4].

## 5. Известное расхождение порядка IPS

Источники не дают одного вечного порядка.

### Актуальная консолидированная карточка

```text
жёсткая конкретизация
→ применяемость
→ активный/связанный контекст редактирования
→ мягкая конкретизация
→ текущее правило подбора ревизии
```

[IPS-A04 §Подтверждённый порядок подбора].

### Историческое ТЗ 2013 года

```text
применяемость по серии/дате
→ конкретизация
→ контекст редактирования
→ конфигуратор
→ правило подбора
```

[IPS-K03 §4].

В этом историческом варианте применяемость имеет short-circuit-семантику: прошедшие по серии/дате ревизии помечаются как выбранные и дальше в подборе не участвуют, непрошедшие исключаются. Поэтому стрелки выше не означают, что конкретизация, контекст, конфигуратор и правило обязательно исполняются для каждой ревизии после применяемости.

### Документ о контекстах

```text
конкретизация → основной/связанный контекст → правило
```

[IPS-K04 §2].

Возможные объяснения:

- эволюция продукта;
- разные профили механизма разрешения;
- разное понимание жёсткой и мягкой конкретизации;
- отдельная предварительная фильтрация по применяемости;
- различия между модулями и конфигурациями.

**Вывод:** порядок для целевой установки заказчика должен быть зафиксирован дифференциальными тестами. Нельзя объявлять один исторический текст «точным IPS» без указания версии продукта.

## 6. Вариантность, замены и аналоги в IPS

### 6.1. Конфигуратор

Опции — самостоятельные объекты с кодом, категорией, типом и допустимыми значениями. Модель задаёт:

- назначенные опции и допустимые значения;
- несовместимости;
- следствия и связанные значения;
- условия включения Occurrence;
- распространение значений вниз по структуре;
- значения по умолчанию и обязательность выбора.

Нужно различать отсутствие значения, явное «не выбрано» и значение по умолчанию. [IPS-A05].

### 6.2. Допустимая замена

Замена принадлежит конкретному родительскому составу и организована в виде групп, вариантов и элементов:

- один вариант актуален;
- другие допустимы;
- один вариант может состоять из нескольких совместно применяемых вхождений;
- поддерживается замена N позиций на M позиций.

Это не выражается одним `replacement_id` или `list<reference>`. [IPS-A05].

### 6.3. Аналог

Аналог — глобальная возможность заменить объект во всех составах, с периодом, приоритетом и режимом подбора. Он не равен допустимой замене конкретной позиции. [IPS-A04].

### 6.4. AutoMatch

AutoMatch использует версионируемый сценарий, типизированные входные данные, ограничения кандидатов, условия и действия. Он может предложить результат либо добавить его в состав. Для воспроизводимости необходимы точная ревизия правила, снимок входных данных, нормализованные единицы измерения и трассировка причин исключения. [IPS-M03 §Сценарий 4], [IPS-A11].

## 7. Целевая модель Interlink

### 7.1. Сохраняется физика вхождения

```text
SourceRevisionId ── типизированное Occurrence ──> TargetIdentityId
```

Каждый конкретный тип Occurrence получает типизированные таблицу, запись, дескриптор и команды. Количество, позиция и порядок сортировки остаются атрибутами Relation. [IL-META §3], [IL-PLM §2].

### 7.2. Точная привязка (Pin)

`PinnedRevisionId` заменяет жёсткую конкретизацию.

Гарантии:

- Pin имеет приоритет над Policy;
- составной внешний ключ доказывает принадлежность Revision целевой Identity;
- Pin изменяется только типизированной командой с соблюдением правил исходных Draft/Revision;
- причина результата — `ExactPin`.

### 7.3. Явный контекст

`ResolutionContext` передаётся аргументом запроса. Он не хранится как изменяемая «текущая настройка» глобального сеанса.

Преимущества:

- два окна могут явно использовать разные контексты;
- фоновая задача получает неизменяемые нормализованные входные данные;
- ключ кеша содержит контекст;
- агентский ContextSnapshot может зафиксировать точные входные данные;
- неподдерживаемое поле не игнорируется.

### 7.4. Наложение Changeset

Контекст редактирования и мягкая конкретизация раскладываются так:

- Changeset содержит Draft и типизированные ожидающие изменения;
- запрос с `ChangesetId` видит собственные Draft;
- временное предпочтение ревизии представлено переопределением Changeset;
- Commit требует снять переопределение либо превратить его в точные Pin;
- объект, затронутый одним открытым Changeset, защищён блокировкой;
- связанная группа изменений обычно становится одним Changeset либо упорядоченным набором.

Неявный режим и автозаполнение больше не требуются. [IL-VERS-CONCEPTS §2], [IL-VERS-SPEC §3, §6], [IL-VERS-IPS §С5–С6].

### 7.5. Применяемость (Effectivity)

Применяемость становится нормализованным типизированным утверждением над объявленными осями:

- встроенные оси: головное изделие, серийный номер, дата;
- значения осей передаются в канонической карте Coordinates;
- диапазоны хранятся как типы диапазонов или строки, а не кодированные строки;
- отсутствие пересечений может обеспечиваться базой данных;
- точная причина указывает сработавшее утверждение применяемости;
- конкретное головное изделие имеет приоритет над wildcard;
- при одновременно заданных координатах серийный номер имеет приоритет над датой.

Coordinates неизменны на всём протяжении обхода OC-A. Распространение значений в области пути относится к OC-B. [IL-PLM §4], [IL-VERS-SPEC §5.3, physical effectivity], [IL-ADR ADR-051–052].

### 7.6. Политика и резервный выбор

Встроенные политики включают Current, Released, Latest, MinMaturity и PinnedOnly. Именованные корпоративные политики позднее будут компилироваться в тот же тракт Query AST/SQL.

Резервный выбор задаётся явно:

- основная политика не возвращает ревизию;
- резервная политика вычисляется только тогда, когда она объявлена;
- причиной результата становится `PolicyFallback(...)`, сопровождаемый предупреждением;
- без резервной политики результатом будет `NoMatch`.

Так сохраняется полезная функция IPS «не совсем подходящая», но она перестаёт маскироваться под обычное совпадение. [IL-PLM §4], [IL-ADR ADR-042, ADR-044].

### 7.7. Контекст состава и включение вхождения (Occurrence)

Общий, конструкторский, технологический или производственный контекст должен быть объявленной в модели осью или значением либо типизированным предикатом Occurrence, а не фильтром, существующим только в пользовательском интерфейсе.

В OC-A:

- выбранные координаты неизменны на всём протяжении обхода;
- условие Occurrence проверяет эти координаты;
- исключённое Occurrence не участвует в подборе ревизии;
- отдельная configuration trace может объяснить проверку условия, но исключённое ребро не получает `ResolutionReason`: оно отсутствует в выбранном графе и не является результатом resolver-а ревизии.

В OC-B:

- значения могут распространяться или переопределяться вдоль ThreadPath;
- вложенные конфигурации могут вводить окружения с ограниченной областью действия;
- точное окружение в данной точке пути становится трассируемым.

Физическая форма полного каталога опций в IR/DSL ещё не реализована окончательно. [IL-META §8в], [IL-ADR ADR-052], [IL-POC §9].

### 7.8. Линия наследования вхождения (Occurrence) и путь

ID связи IPS не решает задачу идентичности позиции между родительскими ревизиями и путями повторно используемых сборок. Interlink вводит:

- реестр линий наследования как опору внешнего ключа;
- неизменяемый `occurrence_thread_id` для каждой линии позиции;
- `ThreadPath` от точного корня;
- сопоставление различий структуры по пути линий наследования;
- привязку замен, фактически изготовленного состава и сигналов к линии наследования или точному пути в зависимости от области действия.

Это позволяет различить одно внутреннее вхождение сборочной единицы, использованное под разными родителями. [IL-PLM §2], [IL-ADR ADR-050, ADR-052].

## 8. Целевой алгоритм разрешения версий Interlink

### Шаг 0. Нормализация запроса

Проверить:

- точный корень или допустимую политику подбора корня;
- поддерживаемый профиль ResolutionContext;
- известные оси и типизированные значения;
- уникальные и известные идентификаторы политик рёбер;
- права доступа и идентичность хранилища;
- политику глубины и циклов;
- совместимость Snapshot, если он указан.

Неподдерживаемые входные данные приводят к отказу до выполнения SQL.

### Шаг 1. Немедленный возврат из Snapshot

Если в запросе выбран совместимый Snapshot:

- проверить вид, корень, определение структуры, артефакт модели и читатель;
- вернуть записанный точный граф;
- не читать актуальные Occurrence и не запускать механизм разрешения повторно.

### Шаг 2. Получить исходящие вхождения (Occurrence)

Для точной исходной Revision:

- выбрать типизированные исходящие Occurrence;
- применить определение и направление Relation;
- сохранить идентификатор, линию наследования и полезную нагрузку Occurrence;
- не терять Occurrence при последующей ошибке разрешения цели.

### Шаг 3. Применить условие включения и варианта

До подбора ревизии определить, включено ли Occurrence в выбранном окружении конфигурации.

Исключённое вариантное ребро не является `NoMatch`: оно не входит в 100%-конфигурацию и не получает `ResolutionReason`. Отдельная configuration trace должна различать «исключено условием» и «включено, но целевая ревизия не найдена».

### Шаг 4. Точная привязка (Pin)

Если Occurrence закреплено Pin:

- проверить точную Revision и её принадлежность целевой Identity;
- вернуть её с причиной `ExactPin`;
- остальные слои подбора не выполняются.

Если Pin отсутствует, но effective policy ребра равна `PinnedOnly`, слои Changeset и Effectivity пропускаются: разрешён только явно заданный fallback профиля либо `NoMatch`. Identity-root нельзя разрешать через `PinnedOnly`; корень такого обхода должен задаваться точной Revision (`GetExactRevision`).

### Шаг 5. Changeset

Если запрос использует Changeset:

- собственный Draft целевой Identity имеет приоритет;
- затем применяется явное переопределение;
- чужие Draft невидимы;
- хост определяет, кому разрешено использовать контекст.

### Шаг 6. Применяемость (Effectivity)

По Coordinates выбрать подходящую зафиксированную Revision:

- конкретное головное изделие имеет приоритет над wildcard;
- серийный номер имеет приоритет над датой;
- отсутствие пересечений действующих утверждений;
- причину, указывающую на сработавшее условие Effectivity.

### Шаг 7. Политика (Policy)

Выполнить запрошенную или заданную по умолчанию политику для каждого ребра:

- сначала проверить допустимость по Maturity и disposition;
- затем выбрать новейшее допустимое поколение для каждой Identity;
- только после этого применить пользовательские предикаты и предикаты Relation.

Это не позволяет фильтру «воскресить» старую удобную Revision.

### Шаг 8. Резервный выбор или NoMatch

- явный резервный выбор → выбранная Revision с предупреждением и причиной;
- без резервного выбора → Occurrence с `ResolvedTarget = null` и причиной `NoMatch`;
- рекурсия через неразрешённую цель не продолжается.

### Шаг 9. Рекурсивный обход

Продолжить от выбранной дочерней Revision:

- дополнить путь Identity и ThreadPath;
- обнаруживать цикл по пути;
- сохранять повторное использование в разных ветвях;
- обеспечивать ограничение максимальной глубины;
- собирать причину и полезную нагрузку для каждого ребра.

### Шаг 10. Проверка полного результата

Для актуального представления частичный результат допустим как диагностическое представление, если это объявлено API. Для бизнес-Snapshot любой `NoMatch`, изменяемый источник или цель, отсутствие права на полный артефакт либо ошибка топологии отклоняет всю публикацию.

## 9. Почему порядок Interlink отличается от IPS

Целевой порядок:

```text
Snapshot → Pin → Changeset → Effectivity → Policy → Fallback/NoMatch
```

Изменение относительно актуальной карточки IPS: Changeset стоит выше Effectivity. Причина — инженер в своём контексте изменения должен видеть собственный Draft, иначе применяемость старой Released-ревизии заслонит будущий состав и проверка изменения потеряет смысл.

Эта перестановка безопасна, потому что:

- Draft виден только при явно заданном `ChangesetId`;
- вне контекста производственные системы и читатели видят только зафиксированные состояния;
- Commit проверяет запланированную Effectivity;
- бизнес-Snapshot не публикует изменяемый граф;
- причина показывает `ChangesetDraft`, а не «применимая Released».

[IL-VERS-SPEC §6], [IL-VERS-IPS §С2].

## 11. Точный заказ: актуальный объект и свидетельство публикации

Важно не смешивать заказ и снимок.

### Заказ как предметный объект

- версионируемая Identity в корпоративной модели;
- строки представлены Occurrence, включая комплект и запасные части;
- объект может изменяться в ходе планирования;
- цены, сроки, статусы и портфель принадлежат хосту или предметному слою;
- публикация представляет собой Released-ревизию под управлением Workflow.

### Snapshot заказа

- создаётся для каждой передачи в производство, отчётность или ERP;
- содержит выбранную 100%-конфигурацию до листьев;
- фиксирует точные исходные и целевые Revision и полезную нагрузку Occurrence;
- несёт происхождение контекста, модели, Policy и настройки;
- неизменяем и хранится в режиме только добавления;
- развитие исходных данных не меняет предыдущую публикацию.

У одного заказа может быть много Snapshot. Формула «заказ хранит один SnapshotId» — только частный случай. [IL-PLM §5], [IL-ADR ADR-052].

## 12. Замены N:M в новой модели

Минимальная целевая семантика:

```text
SubstitutionGroup
  область: точный родительский состав / путь линии наследования Occurrence
  ├─ Вариант A (актуальный/по умолчанию)
  │    ├─ Элемент: линия Occurrence X
  │    └─ Элемент: линия Occurrence Y
  └─ Вариант B (допустимый)
       └─ Элемент: линия Occurrence Z
```

Требования:

- вариант может содержать несколько элементов;
- выбранный вариант должен быть явно указан в свидетельстве разрешения;
- при необходимости область действия различает одну линию наследования под разными путями от корня;
- изменение группы проходит через Changeset исходного состава;
- глобальный аналог не превращается неявно в локальную замену;
- Snapshot хранит выбранные элементы, а не все взаимоисключающие ветви;
- трассировка указывает правило, пользователя или Changeset, выбравшие вариант.

Точное представление IR/DDL ещё не принято как реализованная возможность. [IL-META §8г], [IL-POC §9], [IPS-A05].

## 13. AutoMatch и Expert: где проходит граница

Interlink должен предоставить базовые средства:

- типизированные входные ссылки на Object/Revision;
- алгебру запросов для поиска кандидатов;
- ссылки на точные ревизии модели и правила;
- предложение команды/Changeset;
- ActorContext и корреляцию;
- Snapshot и свидетельства во входных данных;
- стабильные единицы измерения и ограничения значений.

Но сам процесс AutoMatch — предметный или прикладной сервис. Он должен:

- закреплять точную ревизию сценария;
- хранить нормализованные входные данные;
- раскрывать трассировку кандидатов и причин исключения;
- не выполнять произвольный пользовательский SQL;
- разделять `suggest` и `apply`;
- применять результат только типизированной командой Changeset;
- поддерживать политику утверждения агентом или человеком.

Так сохраняется функциональность технологического подбора без второго движка правил и записи внутри ядра.

## 14. Следствия для запросов и хранения

### Индексы

Минимально нужны:

- исходная Revision → Occurrence;
- целевая Identity → обратный поиск вхождений;
- составной внешний ключ, подтверждающий принадлежность Pin;
- уникальность пары «родительская Revision + линия наследования»;
- GiST и запрет пересечений диапазонов для Effectivity;
- допустимость по Maturity, Current и поколению;
- последовательное чтение диапазона Snapshot по `(snapshot_id, seq)`;
- реестр линий наследования и поддержка сравнения по путям.

### Стратегия SQL

- простой уровень: соединения таблиц + SelectRevisionPerIdentity;
- глубокая структура: рекурсивное CTE с SEARCH/CYCLE;
- дорогая Policy: двухфазное вычисление или временная таблица;
- большой поток: серверный курсор;
- стабильный точный граф: чтение диапазона Snapshot.

Физическая стратегия может меняться, но семантика причины и порядок разрешения должны оставаться неизменными. [IL-QUERY §3–§8].

## 15. Семантика ошибок

| Ситуация | Требуемый результат |
|---|---|
| Неизвестная ось, Policy или переопределение ребра | Отказ до выполнения SQL |
| Pin принадлежит другой Identity | Отклонение базой данных или командой |
| Нет допустимой Revision | `NoMatch`, а не скрытое исчезновение |
| Выбран резервный вариант | Явное предупреждение и причина |
| Пересекающиеся условия Effectivity | Отклонение изменения до публикации |
| Неоднозначная замена | Нет 100%-результата; требуется решение |
| Циклы запрещены | Отклонение записи или проверки |
| Цикл встретился в разрешённом графе | Ограниченная трассировка без бесконечной рекурсии |
| Snapshot содержит изменяемую Revision | Отклонение Snapshot целиком |
| Рекурсивный `NoMatch` при создании Snapshot | Ноль строк заголовка и содержимого для идентификатора попытки |
| Права доступа не позволяют прочитать Snapshot целиком | Отклонение артефакта целиком, а не обрезка узлов |
| Несовместимость читателя с моделью или Policy | Безопасный отказ / `SnapshotStale` по ситуации |

## 16. Приёмочные сценарии эквивалентности IPS

1. **Конфликт жёсткой привязки:** применяемость указывает на B, Pin — на A → выбрана A, причина `ExactPin`.
2. **Собственный Draft:** Released-ревизия A применима, собственный Changeset содержит Draft B → B видна только в этом контексте.
3. **Нет совпадения:** допустимой зафиксированной Revision нет → Occurrence возвращается в диагностическом режиме с пустой целью; рекурсия не продолжается.
4. **Резервный выбор:** основные критерии не дали результата, явная резервная политика выбирает Latest → предупреждение сохраняется в API, пользовательском интерфейсе и экспорте.
5. **Граница серии:** серийный номер 100 выбирает A, 101 — B; пересечение отклоняется.
6. **Одна сборочная единица дважды:** полный ThreadPath различает позиции и замены.
7. **Замена N:M:** одна текущая позиция заменена двумя элементами; количества и пути корректны.
8. **Контекст состава:** Occurrence EBOM исключено из представления MBOM без удаления исходной Relation.
9. **Неизвестная опция:** различаются отсутствующее значение, явное «не выбрано» и значение по умолчанию.
10. **Вложенная конфигурация:** переопределение с ограниченной областью действия не протекает в соседний путь.
11. **Обратный поиск вхождений:** новейшая допустимая родительская Revision удалила Occurrence; историческая Relation не «воскресает».
12. **Публикация заказа:** исходное изделие развивается после Snapshot; старый заказ возвращает идентичный побайтово или семантически граф.
13. **Изменение ревизии правила:** актуальный результат правомерно меняется; старый Snapshot сохраняет происхождение и читаемость.
14. **Доступ:** пользователь, не имеющий доступа к одному компоненту, не может создать или прочитать обрезанный бизнес-Snapshot.
15. **Фоновая задача:** контекст не может измениться из-за действия в пользовательском интерфейсе.

| Слой формирования состава | Текущий статус |
|---|---|
| Типы Occurrence/ResolutionContext/ThreadPath | Принятые контракты и сгенерированные формы |
| Хранение и запись Occurrence | План фазы 3 |
| Простой подбор только по Current | План фазы 4 |
| Рекурсивный G4 только по Current + Pin | План фазы 5 |
| Current/Released/Latest/MinMaturity/PinnedOnly + причины | План фазы 6 |

## 19. Итог

Interlink сохраняет ключевую идею IPS: состав — это Relation от состояния родителя к устойчивому дочернему объекту, а дочерняя Revision определяется контекстом. Новая система усиливает эту идею четырьмя средствами:

1. Контекст становится явным и нормализованным.
2. Все слои подбора имеют единый порядок и фиксируют причину.
3. Позиция получает устойчивую идентичность линии наследования и пути.
4. Бизнес-результат фиксируется в полном неизменяемом Snapshot.

Именно эта композиция, а не одноимённый «модуль состава», должна обеспечить прежнюю функциональность IPS.
